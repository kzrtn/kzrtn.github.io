Probably the more 'network-y' and 'IT' feeling part of software development (next to containers that is). Probably because the more finnicky bits of CI/CD belongs to the DevOps team, not the development team.

CI/CD is a software development practice that developers implement and follow in order to automate the building, testing and releasing of code.

For a TLDR;

CI tackles the problem of multiple developers merging their code changes. CI has everyone merge small changes frequently, and every merge automatically triggers a build and a test run. This is so that problems are caught earlier instead of later.

CD automatically packages (compiled, containerized, versioned) the final release and is either made ready to release with a click (delivery) or pushed straight to users (deployment). This streamlines and accelerate bug fixes or new features for users more reliably.

## CI (Continuous Integration)
Includes these steps:
- Lint to keep code clean, maintainable and merge compatible
- Build to put all code together into runnable software bundle
- Test to avoid breaking changes
- Package to put everything together into an easily movable branch

## CD (Continuous Delivery/Deployment)
Includes these steps:
- Deploy to make it available to everyone
- Health checks and rollbacks

For most developers, it's all one pipeline.

CI setups are normally done in a dedicated separate server, keeping it separate minimizes the risk that something else interferes with the CI/CD process and cause it to be unpredictable.

There are two options for this: self-host or use a cloud service.

Jenkins is the most popular self-hosted option. It is incredibly flexible with plugins for almost anything, except it's complicated to set up. There's often a lot of boilerplate code to get builds working.

For cloud-hosted setups, GitHub Actions is a very popular option and what Full Stack Open goes through. Cloud setups are often simpler for most 'normal' usage, but there are often resource limitations (like compute) on cloud-based platforms.

In Full Stack Open, we set up our own pipelines using GitHub Actions.

## GitHub Actions
It's a lot simpler than expected. GitHub Actions work with a workflow (yaml files) written in a specific format, put inside of a repo's `.github/workflows` folder.

<details markdown="1">
<summary>About YAML</summary>
Is a recursive acronym for "YAML Ain't Markup Language". It was originally called "Yet Another Markup Language". Like python, indentations are *very* important in YAML. [See YAML syntax here](https://docs.ansible.com/projects/ansible/latest/reference_appendices/YAMLSyntax.html).
</details>

<br />
It's very convenient that GitHub is both the repository hosting and the CI provider. The [docs](https://docs.github.com/en/actions) were easy to navigate as well.

Workflow files look like this:
```yaml
name: Hello World! ## name of the workflow

on: ## on trigger: the events that trigger the workflow to be executed
  push: 
    branches:
      - main

jobs:
  hello_world_job:
    runs-on: ubuntu-latest
    steps:
      - name: Say hello
        run: |
          echo "Hello World!"
```
Each workflow must specify at least one [Job](https://docs.github.com/en/actions/get-started/understand-github-actions#jobs), which contains a set of [Steps](https://docs.github.com/en/actions/get-started/understand-github-actions#steps).

Jobs are run in parallel, steps are executed sequentially.

There are generally three events that trigger a workflow:
- An event on GitHub (e.g. someone pushes a commit, a pull request is created)
- A scheduled event
- External event occurred (e.g. Slack or Discord trigger)

See more about events that trigger workflows [here](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows).

Workflow files can use secrets too, which are set in the secrets or environment variables of a repo. See [here](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets).

## Good practices
However, I will cover the good deployment practices to keep in mind:
- Anything that can go wrong WILL go wrong. Prepare against that
- Silent failures are VERY bad.
- Deployment system should never leave the software in a broken state.
- It should let us roll back to previous deployments.
- It should handle the situation where a user makes an HTTP request just before/during a deployment
- It should make sure that the software being deployed meets the requirements set before deploying (e.g. don't deploy if tests do not run)

## Hash Versioning
Another important part of software is being able to identify which software version is running. I've already [covered semantic versioning previously here](../../../2026/07/13/node-rest-http.html), so I'll only cover hash versioning here.

Hash versioning (aka SHA versioning) uses a version 'number' in hash, derived from the contents of the repository and the changes introduced in the commit that created the version. This is automatic in Git.

Hash versioning is almost always used in conjunction with automation. However it is error-prone to copy 32 character long version numbers.

Semantic versioning is ideal for official releases, while hash-based versioning (or artifact naming) is better during development. The two systems serve different purposes.

In a typical setup, development builds use hash‑based artifact names. And when code is merged into the main branch, the CI pipeline builds, tests, then assigns a new semantic version number and tags the commit with that version. This is to ensure devs know exactly which version of code they are working with, and that every commit has been tested before release.
